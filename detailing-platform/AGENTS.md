# AGENTS.md

Правила работы над этим репозиторием. Читается агентом перед любой задачей.

## Что это

Мультитенантная платформа записи для детейлинг-студий. Один общий билд
фронтенда, один проект Supabase, разделение по `tenant_id`. Каждая студия
живёт на своих маршрутах `/s/{slug}/` (клиент) и `/s/{slug}/owner/` (владелец).
Добавление новой студии не затрагивает уже опубликованные.

## Состояние среды на момент написания

Проверено 1 октября 2026 в песочнице сборки:

| Что | Состояние |
|---|---|
| PostgreSQL 16.13 | доступен локально, миграции проверяются прогоном |
| npm registry | **закрыт**, 403 напрямую и через прокси; внутреннее зеркало 401 |
| Docker | демон недоступен |
| Deno | не установлен |
| Supabase CLI | не устанавливается (нет npm) |

Отсюда следует: слой БД пишется и проверяется по-настоящему; всё, что требует
установки пакетов (фронтенд, Edge Functions в рантайме, Astryx), пишется как
исходный код, но **не проверяется прогоном**. Любой такой артефакт обязан быть
помечен в `docs/verification.md` как непроверенный.

## Жёсткие запреты

1. **Не выдавать мок за интеграцию.** Если функция возвращает заглушку — это
   пишется в её докстроке и в `docs/verification.md`. Формулировки вида
   «интеграция с X готова» допустимы только после реального вызова X.
2. **Не изобретать API чужой библиотеки.** Props компонентов Astryx, сигнатуры
   методов Supabase и прочее берутся из документации *установленной* версии.
   Пока пакет не установлен — код, зависящий от его API, не считается готовым.
3. **Не генерировать проект одним файлом.** Модуль — одна ответственность.
   Миграция — один смысловой шаг. Потолок ~400 строк на файл; выше — делить.
4. **Клиент не задаёт цену, `tenant_id` и длительность.** Эти значения сервер
   берёт из БД по `service_id`. Любой путь, где они приходят из тела запроса,
   считается дырой.
5. **`service_role` и `LLM_API_KEY` не попадают в бандл фронтенда.** Только
   Edge Functions.

## Слой БД

- Все зависимые таблицы несут `tenant_id`.
- Ссылки между таблицами тенанта — **составные внешние ключи**
  `(tenant_id, id)`, чтобы строка одного тенанта не могла сослаться на строку
  другого. Для этого в родительских таблицах есть `UNIQUE (tenant_id, id)`.
- Занятость ресурса — единственная таблица `resource_occupancies`
  с `EXCLUDE USING gist`. И бронь, и ручная блокировка поста пишутся туда же.
  Отдельной таблицы блокировок быть не должно.
- Создание, перенос и отмена брони — функции `SECURITY DEFINER`, целиком
  внутри одной транзакции. Неудачный перенос не должен терять исходную бронь.
- RLS включена на каждой таблице. `anon` не видит персональные данные,
  платежи и токены — ни напрямую, ни через представления.
- Время хранится в `timestamptz`. Локальные расчёты идут через
  `tenants.timezone`, а не через настройку сессии.

## Соглашения по коду

- TypeScript strict, без `any` и без `!` для подавления проверок.
- Запросы к данным — через TanStack Query, ключ включает `tenantId`.
- Валидация входа и выхода Edge Functions — Zod-схемы в `supabase/functions/_shared`.
- Каждый экран с сетевым запросом имеет четыре состояния: loading, error,
  empty, success. Экран без обработки ошибки не принимается.
- Кнопка без обработчика не принимается.

## Порядок работы

1. Прочитать `docs/plan.md` — там разбивка на этапы и что считается проверкой.
2. Внести изменение.
3. Прогнать проверку этапа (`npm run check:*` или скрипт из `supabase/tests/`).
4. Обновить `docs/verification.md`: что проверено прогоном, что нет.
5. Коммит одним смысловым шагом.

## Проверки

```bash
npm run db:reset      # пересоздать локальную БД и накатить миграции
npm run db:test       # прогнать SQL-тесты из supabase/tests
npm run tenant:new    # создать заготовку business.json
npm run tenant:validate
npm run tenant:publish
npm run tenant:verify
```

Скрипты, требующие npm-зависимостей, помечены в `package.json` и на момент
написания не запускались — см. `docs/verification.md`.
